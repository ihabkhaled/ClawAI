# ADR-168: Save requests are proposed before they are saved

**Status:** Accepted

**Date:** 2026-10-13

Extends [ADR-134](adr-134-ai-decided-save-to-memory-and-context.md). Rule: [rules/57](../../rules/57-memory-and-context-pack-integrity.md) item 11.

## Context

ADR-134 lets a planner model decide that a message is a save request and then saves at once. Two problems showed up. The model picks the memory type, the sentence and the pack for the user, and the user only learns what was stored after the fact. And the keyword pre-filter that decides whether the planner is asked at all was written for English plus a few stems: a corpus of 13 clear save requests per language (13 locales) found recall of 0.08 to 0.85 per language ("from now on always...", "call me X", "put this in my notes", "don't forget" in German, French, Hindi, Chinese and others never reached the planner).

## Decision

- **ASK is the default.** `contextSaveMode: 'ASK' | 'AUTO'` is an optional field on the create-message, edit and regenerate DTOs (the `contextSaveFields` fragment). It is stored on the user message's metadata. Edit and regenerate re-run the turn from that message: a mode sent with them is merged into that message's metadata (`updateMetadata`) BEFORE the re-run event is published, so the re-run honours it; none sent reuses the stored choice (the default ASK when none). The orchestration DTOs do NOT carry it (see "Which surfaces propose" below). With ASK the planner still runs, but its verdict becomes a `PROPOSED` record on the answer, `metadata.contextSave = { status: PROPOSED, sourceMessageId, proposal }`, and nothing is written. The proposal (`ContextSaveProposal`, shared-types) carries the memory type and sentence, the pack source, text, matched `packId` or `newPackName`, and the owner's packs as options. AUTO behaves exactly as ADR-134.
- **The answering model is told the truth.** A PROPOSED record produces a platform note that says the save is PENDING and nothing was saved; the model must not say saved, added or remembered, and gets no link. The note rides in the system prompt and after the final user turn, like every save note.
- **Confirm and dismiss are owner-only, atomic and idempotent.** `POST /chat-messages/:id/context-save/confirm` takes `ContextSaveProposalConfirmRequest` (zod: at least one of memory or pack, memory text up to 4,000 characters, pack content up to the pack-item limit, pack name up to 120, a pack names an existing pack XOR a new one). The thread owner is checked first (anyone else gets 404). The row is claimed PROPOSED to SAVING with `transitionContextSave`, so a double click saves once; the loser gets 409 `CONTEXT_SAVE_NOT_PENDING`. The text the user edited is saved verbatim. A confirm on an already SAVED record returns it. `POST .../dismiss` moves PROPOSED to DISMISSED and clears the proposal; calling it again, or after a save, returns the stored record.
- **One set of limits.** The planner's verdict schema, the confirm DTO and the frontend form all use the same numbers from `save-intent.constants.ts`: memory text 4,000 (a SUMMARY memory is as long as a pack summary may be, so a proposal is never one the confirm refuses), pack name 120, pack content 250,000. The planner's own words are also clamped to them when the proposal is built, and the frontend keeps a test that reads that file so the numbers cannot drift. Pack text is never cut (rule 57 section 1).
- **A named pack is always selectable.** The proposal offers the owner's first 20 packs; the pack the planner matched by name is appended to `options` when the user owns more than 20.
- **A failure puts the card back.** If neither half saved, the record returns to PROPOSED with `proposalError` and the user's edits, and the request fails with that code. If one half saved, the confirm answers 200 with the record back in PROPOSED: the saved half stays on the record (`memory` / `pack`), its side of `proposal` is `null`, `memoryFailure` / `packFailure` name the half that failed (`PLAN` | `LIMIT` | `UNAVAILABLE`) and `proposalError` is the stable code the client translates: `PLAN_FEATURE_DISABLED`, `PLAN_CONTEXT_PACK_LIMIT_EXCEEDED` or `CONTEXT_SAVE_UNAVAILABLE` (`CONTEXT_SAVE_PROPOSAL_ERROR_CODES`; an unexpected throw reports the last). A retry saves only the rest, and a half already on the record is never saved twice, whatever the client sends.
- **A record never stays SAVING.** The claim stamps `savingSince`. Anything that throws after the claim (a client call, the final write) puts the record back to PROPOSED (or NEEDS_PACK_CHOICE for the pack card), keeping the saved half, and rethrows the original error. A SAVING record whose claim is older than 2 minutes (`CONTEXT_SAVE_SAVING_STALE_MS`, or one with an unreadable claim time) counts as waiting again on the next confirm or pack choice; the takeover is itself atomic on the claim time, so two tabs recovering it save once. A SAVING record with NO claim time is refused (`CONTEXT_SAVE_NOT_PENDING`, 409), because without the time there is nothing to compare-and-swap on. When a throw after the claim is released, a half saved by an EARLIER confirm counts as done (`saved.memory !== undefined`), so it is neither re-offered nor marked failed. Memory-service de-duplicates on the source message, so a retry cannot double-write.
- **DISMISSED is final.** One reader (`contextSaveOf`) and one predicate (`isContextSaveSettled`: SAVED, DISMISSED, FAILED) serve every caller: a dismissed proposal cannot be confirmed, chosen on or claimed, and a dismiss on it returns it unchanged. Dismissing a half-saved PROPOSED record (a memory or pack already saved) settles it as SAVED and drops only the unsaved proposal; it is never DISMISSED, since something was saved. `contextSaveModelNote` matches: a PROPOSED record with a saved half says it is partly done, names the saved half with its link, and keeps the rest pending.
- **The pre-filter is wider but still only a net, and a cue is a word, not a substring.** `SAVE_PREFILTER_CUES` adds standing-instruction, address-me, forget-negation, add-to-pack and put-in-notes cues, and verb forms, for all 13 locales; text is folded (case, Arabic diacritics and alef forms, curly apostrophes, and the Persian ZWNJ, which becomes a space on both sides, with no-space spellings kept as cues) before matching, with one regular expression per list so a long message costs a single linear scan. Scripts written with spaces match at a word start (a trailing `$` on a cue also requires the word end: `segna$` does not fire on "segnale", nor "assegna"); Arabic-script cues accept a glued one-letter prefix. Generic words (package/pack words in ar, hi, it, pt, ru, ja, th and zh; "call me", "never use", "добавь", "оставь", "放到", "เก็บ", "ต่อไปนี้", "ノート", bare "सेव", bare "segna", bare "apunta") live in `SAVE_PREFILTER_WEAK_CUES` and count only when two DIFFERENT ones appear; "以后", "今後", "これからは" count only at the start of the message or after punctuation (Chinese, Japanese and Thai have no spaces to bound a word). "Save it/that/this" counts only as the whole message; keep/store and the bare imperatives in other languages count only as the whole short message and only right after an assistant message. A corpus spec (13+ positives, 13 negatives and at least 3 BENIGN messages per language) asserts recall of at least 0.95, a negative pass rate of at most 0.6, and that ZERO benign messages ("Never use var", "Call me back", "Keep going", "Установить пакет", "运行以后会", "ノートパソコン", "क्लाउड सेवा", ...) reach the planner. The planner stays the precision stage.
- **The keyword fallback obeys the mode.** When no planner answers, AUTO still saves what the keyword detector recognised, as before. ASK PROPOSES instead (nothing is written): the same form, built from the detector result, with the user's whole message as the material (or, for a bare "save this", the message above it), the keyword-guessed memory type or a pack named from the content, and a memory too long for the form becoming a pack, kept whole. A bare command with nothing above it still gets the one-line question.
- **Unchanged.** The save-this-message button and the "which pack?" card keep their behaviour; the card now has the same never-stuck-in-SAVING guarantee.

## Which surfaces propose

Only the surface whose backend path runs `ContextSaveOrchestratorManager` carries `contextSaveMode`: **normal chat** (create-message, and the edit and regenerate paths, which re-run the same `handleMessageRouted` from the stored user message). Compare, in-thread Compare, Consensus, Escalation, Best-of-N, Cost Ensemble, Decompose, Pipeline, Repair, Verify and Role Pack run their own orchestration managers, which never call the orchestrator, so a "remember this" typed there is answered by the models as ordinary text. Their DTOs therefore do not accept `contextSaveMode` (a field wired to nothing would be a switch that lies) and the frontend does not send it there. This is a recorded exception to rule 59, listed in `context/chat-surface-parity-map.md`; closing it means routing those managers through the same pre-filter and orchestrator first, then restoring the fragment on their DTOs in the same change.

## Consequences

- A wider net means more ordinary turns pay for one planner call (bounded by the 0.6 budget on the adversarial corpus). Cues that fire on everyday questions must not be added.
- The frontend must render a PROPOSED record as an editable modal and handle DISMISSED.
- Regenerating an answer re-runs the turn and proposes again; only confirm writes, so nothing is saved twice, and memory-service already de-duplicates memory on the source message.
- Orchestration labs, Compare and in-thread Compare do not run the save planner today and do not accept the field (see "Which surfaces propose"). A save request typed there is not proposed.
- The ASK keyword fallback writes no memory without a confirm, at the cost of one extra click when the planner is down.
