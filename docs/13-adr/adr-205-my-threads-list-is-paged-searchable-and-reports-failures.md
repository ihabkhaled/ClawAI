# ADR-205: The "My Threads" list is paged, searchable, filterable and reports failures

**Status:** Accepted

**Date:** 2026-10-31

Builds on [ADR-174](adr-174-threads-refuses-what-cannot-succeed-before-it-queues.md) (owner generation rules) and [ADR-201](adr-201-thread-progress-is-pushed-over-sse-with-polling-fallback.md). Rules: [rule 07](../../rules/07-backend-controllers-and-transport.md), [rule 11](../../rules/11-dtos-and-validation.md), [rule 18](../../rules/18-error-handling-and-reliability.md), [rule 52](../../rules/52-every-prisma-schema-ships-its-migrations.md).

## Context

`GET /thread-publications/mine` returns at most 50 rows with no search, no filter and no failure information, and the job state (queued, failed, cancelled) lives in the generation service, not in the Threads database. The owner's list page needs paging, title search, a status filter with a correct total, and a reason when a Thread failed.

## Decision

- **Endpoint.** `GET /api/v1/thread-publications/mine/page?page=1&pageSize=10&q=&status=ALL` (owner only; the old `mine` is unchanged). Validation (`ZodValidationPipe`, the standard 400 `Validation failed`): `page` 1..100000, `pageSize` 1..50 (default 10), `q` trimmed, at most 100 characters, no NUL or lone surrogate (blank = no search), `status` one of `ALL | GENERATING | READY | PUBLISHED | FAILED`.
- **Response.** `{ items, page, pageSize, total, totalPages }`, newest first (`created_at desc, id desc`, so pages never overlap or skip). A page past the last returns `items: []` with the real `total`. `totalPages` is `ceil(total / pageSize)` (0 when empty). Each item: `id`, `title`, `slug`, `createdAt`, `updatedAt`, `status`, `publishedAt`, `failure { code, retryable, step } | null`, `canPublish`, `canDelete`, plus the added `publicationStatus` (the stored status). `slug` is set only for a PUBLISHED article (a draft's slug is not a public address).
- **Status.** PUBLISHED = live. READY = READY_FOR_REVIEW, UNPUBLISHED, or a DRAFT whose job finished (WAITING_FOR_REVIEW or COMPLETED). FAILED = the job FAILED, the job was CANCELLED (a cancelled job counts as FAILED with `failure.code = JOB_CANCELLED`, retryable, because retry accepts it), or the publication was REVOKED by moderation (`PUBLICATION_REVOKED`, not retryable). GENERATING = a DRAFT whose job is queued, running, or not read yet.
- **Where the job state comes from.** The Threads database never knew it, so a filter and a COUNT could not be pushed into SQL. The publication row now stores the last known state (`generation_state` GENERATING, FAILED, CANCELLED or DONE; `generation_failure_code`, `_step`, `_retryable`, `generation_state_checked_at`). Additive migration `20261031090000_threads_generation_state`: new nullable columns, the default GENERATING for new rows, existing rows stay NULL ("not read yet"). Before each list the service reads, from the generation service, the owner's DRAFTs whose state is NULL or GENERATING and was read more than 30 s ago (at most 20 rows, 5 at a time, 4 s each, never fatal: if the generation service is down the rows keep saying GENERATING and the list still answers) and stores the answer with a guarded `UPDATE` that does not move `updated_at`. A finished job's draft is saved then (the same `savePrivateDraft` the publish path uses), so READY means the owner can open it. FAILED reads the progress snapshot for the failure's own code, step and `retryable`. A terminal state is never read again; a retry (`attachRetryJob`) resets it to GENERATING. No event consumer was added: lost events cannot leave a row wrong because the next list heals it. A job that finishes is shown as GENERATING for at most 30 s.
- **`failure.code`.** The stable machine code the frontend already maps (`THREAD_GENERATION_CODE_KEYS`), checked against `^[A-Z][A-Z0-9_]{1,63}$` before it is stored and again before it is returned; anything else becomes `GENERATION_FAILED`. Codes owned here: `JOB_CANCELLED`, `GENERATION_JOB_MISSING` (the upstream job is gone, not retryable), `PUBLICATION_REVOKED`, `GENERATION_FAILED`. Never provider text, never a secret.
- **`canPublish`** = status READY_FOR_REVIEW or UNPUBLISHED and a revision matching `PUBLISHABLE_REVISION_WHERE`, the one constant `publishReadyRevision` now also uses. An already PUBLISHED article is false (publish is idempotent, so a repeat is harmless, but there is nothing to offer). **`canDelete`** = status DRAFT, READY_FOR_REVIEW or UNPUBLISHED (`OWNER_DELETABLE_PUBLICATION_STATUSES`) and not a DRAFT whose job is running or unread. Tests run the real publish write and the real delete service over every status and job state and require the same answer.
- **Search.** The title the list shows (the newest revision's, or the newest approved one while a newer revision is STALE or PENDING, exactly `pickOwnerListTitle`) is chosen in SQL with two `LEFT JOIN LATERAL ... LIMIT 1` probes on the unique `(publication_id, revision)` index, and matched with `ILIKE $n ESCAPE '\'` on a bound pattern. `%`, `_` and `\` are escaped, so user text is literal; there is no regex, so no ReDoS; quotes are only ever a bound value. It is a scan bounded to the owner's own rows (index `(owner_id, created_at)`), not an index lookup; an owner has tens to hundreds of Threads. A title still shown as the "Untitled draft" placeholder is derived at read time and is not searchable by its derived text.
- **Efficiency.** One SQL for the page ids, one `COUNT`, then three queries for the whole page (rows with a 25-revision window, publishable revisions, placeholder titles). No per-row query. No new index.
- **Isolation.** Every query is `WHERE owner_id = $caller`; hydration re-checks the owner. A stranger gets an empty list and cannot count another user's rows.

## Existing owner rules, verified

Delete: DRAFT of a failed or cancelled job is deleted (job removed upstream, then the row); a running job is `409 Cancel the running generation before deleting it`; PUBLISHED or REVOKED is `409 Unpublish the publication before deleting it`; a second delete is `404` (the row is gone). Unpublish: a never-published Thread is `409 THREAD_PUBLICATION_NOT_PUBLISHED`; an already UNPUBLISHED one answers the same 200 again. Publish: idempotent for a live article; a DRAFT is `409 ... no approved revision ready`. A stranger gets `404` on all of them.

## Consequences

One additive migration, deployed with the service (`prisma migrate deploy` runs at start). Old rows are read once on the owner's first list. If the generation service is unreachable for a long time, such rows show GENERATING and are not in the FAILED filter until it is back. Rolling back the code leaves the columns unused and harmless. A per-event update (the completed and failed events already exist) would remove the 30 s window and is the natural next step.
