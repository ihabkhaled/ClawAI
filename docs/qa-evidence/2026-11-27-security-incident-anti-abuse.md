## Findings

- Docker published every database, Redis (no password), MongoDB, RabbitMQ, ClamAV and the frontend on 0.0.0.0; ufw was
  off. An SSH key was planted in Redis (failed: protected configs). Fixed on the host and in the repo (rules/68).
- Seven internal controllers trusted any caller on the Docker network; three routing-service and two other callers sent
  no service token (chat's workspace search was silently failing). All guarded and fixed.
- A bot farm signed up 113 throwaway accounts from rotating addresses; per-address limits cannot stop that.
- Windows Smart App Control blocks @swc on this PC: service tests ran in a Linux container / no-swc config instead.

- The repo-wide fetch-guard test caught the captcha adapter calling `fetch()` with no host allow-list; fixed before
  the push (`CAPTCHA_VERIFY_HOSTS`, adapter spec).
- The first release attempt stopped before building: two production `.env` port values already carried
  `127.0.0.1:`, which the compose file now adds itself. Reset to bare numbers; the re-run deployed.

## Production after release 1.244.0

- No-account probe against https://claw-ai.co: 5/5 (bot-check config with proof of work, 428 without it,
  400 `DISPOSABLE_EMAIL` for mailinator and euploading after a solved proof of work, 403 on a reused challenge).
- Migration `20261127120000_anti_abuse_user_devices` applied; 0 unhealthy containers; 0 real 401 responses in the
  15 minutes after the deploy in the eight services whose internal routes or callers changed; an internal route answers
  404 from the internet.
