## Findings

- Root cause of the raw keys: two template keys (`threadPublicReport${reason}`, `threadChangeRequest${status}`) lost the `chat.` prefix; `t()` returns the key when it does not resolve, the key test only matched `t('literal')`, and component tests echoed the key. Fixed with literal maps; the key test now rejects template keys and reads quoted `chat.`/`common.` literals in components, hooks, constants, utilities and pages. No other dynamic `t()` call under the Threads files builds a key without a prefix (grep of components/threads, hooks/threads, both threads route folders, the marketing threads components).
- Reaction highlight: the public `GET .../reactions` endpoint always returns `viewerReaction: null`. Frontend stop-gap shipped (localStorage per user and Thread, fills only the null). Backend part NOT done: make that read optional-auth in threads-service.
- The frontend contract tests read the service enums; the backend work in flight added `QUEUE_EXPIRED` and six start-refusal codes, which failed `thread-generation-code-keys.test.ts` until keys existed. Added them (extra to the brief). The sentences are inferred from the enum comments and should be checked against the final backend behaviour.
- Draft preview was a scrollable `<pre>` axe flags; it is now a read-only `Textarea`. Step excerpts no longer scroll.
- Shared status tokens (`text-warning`, `text-info`, `text-success`) fail 4.5:1 on white in the light theme. Not changed globally; Threads uses dark shades plus `dark:` tokens.
