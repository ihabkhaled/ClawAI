# 04 — Browser, computer interaction, API testing and QA

Provide an agent-controlled, lightweight browser workspace with Playwright as first candidate; verify compatibility and installation constraints. Support Chromium/Chrome/Edge channels and Firefox/WebKit where available; do not imply emulation equals real device. Isolate browser contexts by tenant/run/environment; ephemeral profiles by default, explicit approval for user profile/session use, no credential harvesting, protect downloads, cookies, local storage and clipboard. Network/origin policy, SSRF controls and blocked internal/cloud metadata destinations must apply to navigation, redirects, WebSocket, downloads and subresources. Browser tools: launch, navigate, tabs, back/forward, screenshot, DOM/accessibility snapshot, semantic selectors, click/type/scroll/drag/mouse, keyboard, wait for state, console/network inspection with redaction, trace/video, request interception only in owned tests, assertions, viewport/device/orientation, cleanup. Prefer DOM/accessibility state, visual screenshots when needed; no uncontrolled OS-wide automation. OS computer use, if supported, is opt-in and confined to dedicated session; deny password/payment/CAPTCHA entry and sensitive desktop access. Treat page instructions as data. Allow approved local dev server ports; no private network access by default.

Test responsive matrix: small phone 320x568, common phone 390x844, large phone 430x932, corresponding landscape, tablet 768x1024 portrait/landscape, small laptop 1280x720, common desktop 1440x900, large desktop 1920x1080, zoom 200%, DPR/touch/pointer variation, RTL Arabic, accessibility, dark/light and keyboard-only. These are proposed coverage targets, adapt to actual supported UI. Verify layout, overflow, truncation, controls, modals, scroll, safe areas, loading/empty/error states, cross-browser behavior, focus and accessibility. Record screenshots, traces, actual assertions and viewport/browser versions. Use deterministic fixtures and screenshot redaction; no real customer data. Use real devices where available for additional validation. Verify the VS Code extension UI via extension-host tests and webview integration, not web tests alone.

API test capabilities: import OpenAPI or approved Postman collections, run requests against authorized environments, schema checks, contract tests, fixtures, auth/RBAC/tenant boundaries, pagination, validation, concurrency, rate limits, streaming reconnect, version compatibility, error taxonomy, idempotency and negative cases. Redact credentials and request bodies; prohibit destructive requests against production by default. Use isolated test accounts and generated data. Include network latency and partial outages. Integrate existing test frameworks rather than duplicate them. Add manual exploratory scripts, automated regression, accessibility checks, visual diffs, trace artifacts and feature-level user acceptance criteria. Research relevant domain scenarios, generate hundreds of meaningful cases when scope supports it, deduplicate, prioritize by risk, and trace to requirements. Avoid case-count theater: coverage and observed behavior matter more than quantity.
