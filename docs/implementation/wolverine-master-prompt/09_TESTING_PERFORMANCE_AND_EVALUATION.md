# 09 — Full SDLC validation, QA and performance

Create a risk-based test catalog traced to requirements and actual implementation. Cover business rules and acceptance from product owner, business analyst, project manager, customer, end user, accessibility reviewer, manual QA, automation QA, architecture, security, SRE and performance perspectives. Use Given/When/Then, preconditions, fixtures, steps, expected outcomes, evidence, priority, environment and owner. Include positive, negative, boundaries, permissions, concurrency, timezones, locale/RTL, quotas, data integrity, migration, backward compatibility, accessibility, install/update/uninstall, offline/reconnect, errors, recovery and usability. Test actual application behavior, not just model-generated claims. Product owner/customer acceptance is simulated or actual, explicitly distinguish the two; obtain required human sign-off. No fake acceptance on their behalf.

## Layered test strategy

Unit/property tests for parser, schema, authorization, cost accounting, tool arguments, retry logic, state transitions, redaction, dedup and fingerprinting; integration for backend/extension/provider, database, queue, tool runner, Git fixtures and browser; contract tests for all supported provider protocols, tool schema versions and API backwards compatibility; end-to-end with a real extension host, test repositories, local servers, Playwright, test GitHub/SSH/deployment environments with authorization; regression tests for each fixed incident; chaos tests for network, provider disconnect, worker crash, queue saturation, DB downtime, expired tokens and partial writes; visual and accessibility regression; isolated security tests from 08; load, stress and soak. Use mocked adapters for deterministic coverage and authorized live smoke tests for real behavior. Separate real provider evaluations from synthetic tests, use fixed snapshots and record versions. Never treat mocks as proof live integrations work.

## Required scenario families

- Multi-hour coding session (6h minimum target) with frequent tool calls, stream disconnect/reconnect, intermittent provider errors, context compaction, extension reload and resumed state. Verify no premature terminal state, duplicated action, lost accepted checkpoint, unauthorized calls or uncontrolled cost.
- Git fixture with failing hooks, conflict, rejected push, CI failures and flaky tests. Prove genuine fixes, exact SHA checks and protection integrity; simulate denied approval, stale branch and ambiguous push. Test protected-branch policy and release gating.
- Browser device/engine matrix, API auth and schema, user acceptance workflows and cross-repo compatibility as in 04. Verify artifacts and human-readable reports.
- Three-model mode: role conflicts, malformed adviser, compromised adviser, unavailable provider, budget and cancellation, confidential file boundaries, advice rejection, actual improvement on controlled tasks.
- Wolverine full loop: seed benign defect in disposable test version; trigger from test extension; verify local capture/redaction, authenticated ingestion, dedup, correlation, ticket, sandbox reproduction, test-before/fix-after, independent review, draft PR, staged CI, approved prerelease, notification, install/update, monitoring and rollback. Run duplicate/replay/flood/injection variants; confirm no unauthorized publication. Validate non-reproducible case stays blocked; verify agent failure cannot recursively spawn unbounded agents.
- Performance: stream first event/first answer, tool latency, indexing time/memory, parallel advisory overhead, extension CPU/RAM, queue lag, ingestion cost, backend p50/p95/p99, error rates, provider cost, job throughput, time-to-triage/fix and release success. Profile bottlenecks; benchmark against pre-change baseline under controlled workload.

## Suggested initial targets — calibrate with baseline and approve

No unauthorized privileged effects or known critical vulnerabilities in release candidate; zero synthetic secret leaks in scoped fixtures; no duplicate effects in replay/idempotency test suite; 100% required CI checks on exact SHA; p95 core API latency overhead due to telemetry <=5% under normal baseline load; extension telemetry enqueue non-blocking with bounded local storage; interactive system stable when telemetry is saturated; queue backlog recovered within documented SLO; explicit budgets prevent runaway model calls and retries. Establish numeric availability, incident detection, triage and recovery SLOs after measuring baseline, with owners and error budgets. Do not confuse finite tests with proof of zero vulnerabilities.

## Repeated testing and gates

Generate hundreds of meaningful cases across scenario families; use combinatorial/property/fuzz coverage rather than duplicate superficial cases. Run as many as 1,000+ automated executions where justified (including varied seeds, OS/browser/provider, fault injection and adversarial fixtures); record exact distinct cases vs repeated runs, environment, seeds, pass/fail/skip/flaky and artifacts. Never claim 1,000 runs if not executed. Run expensive soak/load/security suites in scheduled CI with capped authorized traffic and resources. Fix root cause, rerun targeted and relevant broader regression, re-audit critical changes. Stop when objective acceptance gates are met or genuine blockers remain; no infinite audit loops. Keep failed-run evidence. Produce comparison matrix, risk register, traceable reports and release recommendation. Testing must finish on local isolated fixture before staging, then authorized production canary with nondestructive synthetic checks.
