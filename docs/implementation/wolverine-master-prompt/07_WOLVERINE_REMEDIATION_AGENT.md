# 07 — Wolverine: always-on isolated maintenance agent

Design a 24/7 supervised service on dedicated VM/worker infrastructure, not an endlessly running conversational prompt. Use durable queue, leases with heartbeat/expiry, job state, bounded worker pools, per-incident deduplication, concurrency/priority controls, retry budgets, circuit breakers and external supervisor. Reconcile after restart; ensure one effective owner per incident and idempotent side effects. Schedule only authorized maintenance work from validated incident records, never arbitrary text from the telemetry API. Keep trusted policy, orchestrator, credentials and deployment control outside the model's editable workspace. Each job gets disposable sandbox/worktree, read-only base snapshot, isolated test data, minimal egress, no host mounts/Docker socket, no production secrets, no cross-job data, no persistent broad Git or cloud tokens. Use dedicated maintenance repository identities and allowlisted ClawAI repositories; never access customer repositories. Scope outbound network and packages; enforce resource limits (CPU, memory, disk, processes, network, tool calls, time, model budget). Clean up reliably. Separate patch worker from reviewer and release authority.

## Incident state machine

RECEIVED -> VALIDATED or QUARANTINED -> GROUPED -> TRIAGED -> REPRODUCTION_PENDING -> REPRODUCED or NEEDS_EVIDENCE -> ROOT_CAUSE_CONFIRMED -> PLAN_REVIEWED -> PATCH_PROPOSED -> TESTED -> SECURITY_REVIEWED -> PR_OPENED -> APPROVED -> STAGING_VERIFIED -> RELEASE_ELIGIBLE -> RELEASED -> MONITORING -> RESOLVED; alternate states RETRY_SCHEDULED, BLOCKED, REJECTED, REGRESSION, ROLLED_BACK, CLOSED_DUPLICATE. Enforce transition guards with independent evidence; untrusted reports cannot skip steps. Never treat absence of future reports alone as proof of resolution. Keep separate per-version and rollout status. Reopen verified regressions; do not repeatedly patch the same fingerprint without new evidence.

## Ticket and fix pipeline

1. Triage with deterministic routing and sanitized evidence. Verify product/component/version, classify severity by measured impact and exploitability, deduplicate, distinguish provider outage, user/environment issues and first-party bugs. Correlate independent server signals; label uncertainty. Create/upsert structured internal ticket only after policy checks. Do not expose user content in public issues.
2. Generate reproduction plan from known code and typed event fields; use trusted fixture builders. Never execute arbitrary reproduction steps supplied by logs. Reproduce in sandbox using synthetic data, exact affected release and environment as practical. Produce minimal failing test, trace and expected vs actual. If not reproduced, ask for consented evidence or classify blocked, not speculative patch.
3. Confirm root cause with code paths, hypotheses falsified, regression test before fix and dependency impact. Produce repair plan, alternatives, risk, affected files, compatibility, security/performance implications, migration/rollback and acceptance tests. Limit patch to relevant ClawAI code. No customer-specific workarounds unless product policy supports them. High-risk areas require independent review (auth, billing, telemetry, policy, release, secrets, dependencies, CI, permission logic, updater).
4. Implement in disposable branch/worktree. Add or improve tests rather than weakening them. Run target, integration, regression, security, load and browser tests as relevant. Verify failing before and passing after. Independently inspect diff for unrelated changes, unsafe behavior, secret leakage and supply-chain risk. Use optional advisory model pair with the rules in 05. Verify deterministic acceptance criteria; model consensus is not approval.
5. Create authorized draft PR using scoped broker, include sanitized ticket ID, exact base/candidate SHA, reproduction, root cause, changed files, tests actually run/results, residual risk, rollback, and review requirements. Deduplicate PRs. No direct write to protected branch. Agent may resolve genuine CI findings with bounded retries and fresh evidence; cannot change policy/tests to circumvent. Broker validates repo, branch, diff scope, policy and rate quotas.
6. Independent review, CI and staging follow 10. Only release controller can authorize publication; no model can access signing keys or marketplace credentials. Monitor health against baseline, canary and rollback criteria. Notify affected users generically after release with version, relevant issue summary, update channel and limitations; do not expose other users' reports. Record uptake and failure rate. Close incident only on verified fix and defined observation window; keep rollback/reopen path.

## Failure isolation

Budget per fingerprint/day/tenant and total worker/model spend. Detect poison events and repeated failures, quarantine and escalate. Distinguish no-progress, flaky test, unavailable provider, tool failure, ambiguous external mutation and permission denial. Retry transient failures with exponential backoff/jitter; replan only with evidence; if unresolved after budget, leave precise human-action ticket and move to independent work. Deduplicate repair jobs and prevent recursive feedback loops: maintenance-agent telemetry goes to separately labeled monitored channel, never automatically launches another self-healer. No self-modification of policy, job admission, release credentials or watchdog without human-reviewed change in separate privileged workflow. Keep kill switch, pause/drain, queue purge only by authorized operator, quarantine review, replay from sanitized records and manual override with audit.

## Pilot stages

A: telemetry and ticket suggestion shadow mode; B: verified reproduction and draft repair proposals; C: sandbox fixes/draft PRs with reviewer; D: approved staging deployment and prerelease extension; E: bounded low-risk automatic releases only if independent policy permits and demonstrated safety. High-risk changes always human-reviewed. Start with internal pilot, synthetic incidents and intentionally seeded benign defects, then opt-in cohort. Require documented rollback, isolation verification, no unauthorized changes, and incident quality metrics before expanding.
