# 06 — Wolverine: privacy-preserving diagnostics and secure ingestion

Goal: convert every meaningful ClawAI failure into structured evidence and actionable, reproducible engineering work, without collecting excessive personal data or allowing attacker-controlled inputs to command the maintenance agent. Coverage includes extension, extension-host/webview IPC, backend, model gateway, provider API/stream, auth, billing, tools, Git/CI integration, browser automation, MCP, state transitions, retries, crashes, timeouts, malformed output, observed inconsistencies, suspicious hallucination signals and recoverable/terminal failures. Do not claim to detect every hallucination; record verifiable mismatch evidence and label uncertain signals. Capture recoverable failures even if user ultimately succeeds, with aggregation to avoid a log storm. Track successes as denominators. Diagnostics must never delay the interactive path; provide opt-in detailed incident sharing and safe offline behavior.

## Proposed architecture (validate against repo)

Extension diagnostic SDK -> bounded local queue and batch uploader -> authenticated ingestion gateway -> schema/size validation, tenant/rate/abuse policy -> durable event queue -> normalization/redaction/deduplication -> incident grouping and priority -> sanitized incident store -> isolated maintenance scheduler. Separate metrics, traces and logs; use OpenTelemetry where compatible. Raw event payloads never reach a model with privileged tools. Separate interactive data plane, diagnostics plane, remediation plane and release control plane. Queues are bounded with DLQ, TTL, lag monitors, backpressure and per-tenant fair scheduling. Never directly spawn a model, shell, Git job or deployment in the request handler. All cross-plane actions require independently issued scoped capabilities.

## Event contract

Versioned schema: event_id (unique), event_type (enum), observed_at/server_received_at, installation_id (pseudonymous), tenant_scope derived server-side, session/run/step/tool_call IDs, trace/span IDs, sequence, extension/backend version, OS/runtime family, provider/model ID (if permitted), tool name/version, operation class, environment label, normalized error code, sanitized message/stack fingerprint, severity, attempt count, elapsed bucket, outcome, retryable, recovery result, optional scrubbed evidence reference, consent category. Server adds request provenance, authentication assurance, validation and trust status, policy version and grouping key. Never accept tenant, roles, approval, severity, repository path or destination as trusted client authority. Reject unknown fields where practical; strict enums/lengths, depth and array caps, timestamp skew bounds, decompression and batch byte limits. Validate at extension and server; enforce server-side independently. Use deterministic parsing and parameterized database access, never evaluate payload strings or concatenate into SQL/shell/template instructions. Store a content hash for integrity without retaining secrets. Schema evolution and backward compatibility are mandatory.

## Privacy and retention

Default telemetry: minimal metadata, no raw prompts, source code, user files, full command lines, environment variables, auth headers, tokens, SSH keys, Git credentials, cookies, request/response bodies, screen recordings or customer repository URLs. Local redaction before transmission plus server-side redaction/quarantine; structured allowlists, not regex alone. Optional user-reviewed diagnostic attachment flow with preview, explicit scoped consent, secure upload, separate retention, encryption, tenant isolation and access logging. Never use customer data for cross-tenant training/reproduction by default. Build sanitized synthetic fixture from evidence; request additional information only with consent. Document what is collected, legal basis where applicable, opt-out, deletion, retention and access controls. Propose retention limits (e.g. 7 days for optional attachments, 30 days for sanitized events, longer aggregate metrics only) subject to legal/security review; delete from derived stores and backups according to published policy. Prevent user identity disclosure in issue titles, PRs and logs. Provide operator-only access with RBAC and audit. Redact error and debug output from telemetry about telemetry itself.

## Authentication and abuse resistance

Use existing secure account auth, short-lived audience/scope-bound access tokens; server derives tenant and installation ownership. Bind enrollment to authenticated user/session and registered per-installation key where supported (e.g. OS secure key store), with proof-of-possession/request signing covering method, path, body hash, timestamp and nonce; check replay cache, clock skew, key rotation/revocation and session expiration. Use TLS and hardened ingress; consider mTLS for service-to-service identities. Do not embed universal secret in distributable extension. Signed events prove possession of credential, not genuine client code or truthful event content; client is hostile by assumption. Add attestation only where supported and never as sole trust. Correlate backend-generated independent evidence, version/release manifest, known fingerprints, reproducibility and anomaly signals. Reject or quarantine forged, impossible, suspicious and uncorroborated reports; do not punish genuine users on heuristics alone. Separate public auth/API rate limits from telemetry. Rate-limit per IP/account/tenant/installation/key and global resource, enforce request/byte/batch/concurrency/queue caps, progressive throttling, duplicate suppression, bounded retry-after with jitter, WAF/CDN where relevant, bot/abuse detection, fair tenant quotas and hard daily cost limits. Handle many low-rate accounts, valid compromised installations, IP rotation, replay and queue flooding. Load shedding should drop low-priority repetitive diagnostics before critical sanitized signals; never degrade core coding API. Use cheap checks before expensive work and do not rely on model classifiers to protect ingress. Add circuit breakers and kill switches for uploads, triage, jobs and release; admin operations separately authenticated and audited.

## Incident quality and observability

Deduplicate by stable normalized error fingerprint + affected version/component + contextual evidence, not arbitrary client title. Preserve counts, first/last seen, recovery success, affected versions and verified impact while limiting cardinality. Group across tenants only after sanitization with no tenant data leakage. Separate client-reported from server-observed metrics. Build dashboards for event acceptance/rejection, rate-limit hits, duplicate ratio, lag, DLQ, cost, redaction, incident volume, crash-free sessions, recovery ratio and telemetry overhead. Escalate suspicious bursts to security operations rather than maintenance execution. Ensure event delivery is best-effort, durable when appropriate and at-least-once with idempotent ingestion; do not promise exactly-once transport. Simulate network loss, crash before flush, duplicates, out-of-order events, overload, schema mismatch and redaction failures. Gate: no raw secrets or tenant data leave approved boundaries; no malicious payload triggers privileged work; core latency and availability remain within agreed budgets under load.
