# 10 — Cross-repository delivery, signed releases, deployments and updates

Inventory actual GitHub Actions workflows, branch protections/rulesets, CODEOWNERS, environment approvals, extension packaging/publishing channel (VS Code Marketplace, Open VSX, GitHub Releases as actually configured), versioning, Docker/SSH/host infrastructure and backend-extension compatibility. Do not assume credentials or production access. Use least-privilege GitHub App identity or scoped token; separate PR writer, CI, deployer and publisher. OIDC/short-lived credentials where supported; protect signing/publishing secrets in isolated release environment. Never expose secrets to code from untrusted PRs; avoid dangerous event/workflow patterns and pin third-party actions to reviewed immutable SHAs. Protect CI, approval logic and release workflows from agent-controlled modification without independent review. Build from reviewed exact SHA, verify dependencies/lockfiles, SBOM and vulnerability scans, artifact hashes/provenance/attestations and signed release manifest where supported. Verify artifact corresponds to source, never execute arbitrary downloaded artifacts without checks. Define deterministic reproducibility where feasible and document exceptions.

Release controller independently checks approved PR, required tests/security checks, artifact provenance, allowed change class, exact source digest, version increment, API compatibility, rollback and environment approvals. High-risk changes (security, auth, billing, policy, updater, CI, migrations, secrets, new permissions/dependency trust) always require human approval. Low-risk automation only after staged pilot and explicit policy authorization; use pre-approved narrow change classes, quotas, independent review and no ability for repair agent to override. Never automatically merge arbitrary telemetry-driven code. Default draft PR and prerelease. Verify actual remote checks and deployment rather than assuming success from local commands. No publishing from a dirty workspace.

Deployment sequence: local validated -> CI exact commit -> staging integration and smoke -> controlled prerelease/internal cohort -> production canary -> monitor SLO/security/rollback criteria -> gradual expansion -> general availability. Use versioned config/migrations, backward-compatible expand/contract where feasible, verified backups and recovery rehearsal; stop on incompatible backend/extension versions or error budget breach. Track release ID, commit, artifact hash, environment, publisher, approval receipts, timestamps and smoke results. Roll back to known-good version or disable via feature flag; extension downgrade/recovery must account for state/schema and Marketplace constraints. No production destructive tests. Release health gates independent of agent output. Establish kill switches for new capabilities, diagnostics, model collaboration, self-healing scheduling and publishing. Document manual override and incident response.

User UX: announce approved update only after publication is verified; show version, sanitized changelog, compatibility and update instructions; respect existing VS Code auto-update setting, avoid forced installs or restarts and do not claim install occurred until observed with permitted telemetry. On issue resolution, surface generic affected-version notice without revealing report details. Track adoption, crash/incident frequency, regression and rollback. Run update/install/uninstall tests on supported versions and OS. For each release provide evidence packet and known issues; notify on rollback or superseded release. CI/CD fixes must address actual errors, never bypass checks. Use bounded retries, verify outcomes, maintain precise blockers.
