# Wolverine incident intake and self-healing: threat model

Status: Draft for B1 (2026-11-28). Review by an independent security owner is still to do.
Decision: [ADR-229](../13-adr/adr-229-wolverine-planes-and-incident-intake.md).
Plan: [self-healing-coding-agent-plan.md](../implementation/self-healing-coding-agent-plan.md) sections 5 to 8.
Tests: [adversarial-suite-catalog.md](../16-quality-engineering/wolverine-adversarial-suite-catalog.md) (ADV ids below).
Style follows [routine-secrets-threat-model.md](routine-secrets-threat-model.md).

This document is written before any intake code exists (security before the feature). Nothing here claims 100 percent
security. Every control is a promise to build and test, not a fact, unless it is marked [V].

Legend used in the tables:

- **[V]** verified by reading the named file on 2026-11-28.
- **[N]** a NEW component that does not exist yet.
- **[U]** unverified: the code or setting was not read, or does not exist yet. Settle it in the batch named.
- L and I are likelihood and impact: L (low), M (medium), H (high).

## 1. Scope

In scope: the path from the extension's diagnostic SDK to the incident store (B4, B5), the healer VM and its GitHub
identity (B7, B8), and the release controller (B9). Out of scope: the interactive chat and coding path itself (its own
rules apply), repair of customer repositories (a non-goal), and the correctness of generated patches.

## 2. Assets

| Id  | Asset                                                | Why it matters                                                                               |
| --- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| AS1 | Users' code, prompts, files, credentials and tokens  | The extension runs next to them. A report must never carry them out.                         |
| AS2 | The extension's users, through a release             | A malicious or broken release reaches every installed copy. This is the highest-value asset. |
| AS3 | Backend availability and cost                        | Flooding or amplification takes the chat API down or burns model money.                      |
| AS4 | Incident store integrity                             | Fake or poisoned incidents steer the healer.                                                 |
| AS5 | ClawAI repositories, branches, workflows, policy     | The healer writes here. A hijacked healer rewrites the product.                              |
| AS6 | Release channel, signing and Marketplace credentials | Publication is irreversible for installed users.                                             |
| AS7 | Healer VM and its identities                         | A foothold for lateral movement.                                                             |
| AS8 | Audit trail and kill-switch config                   | Control of the safety levers.                                                                |
| AS9 | Privacy of reporters (pseudonymous ids, tenants)     | Legal and trust exposure.                                                                    |

## 3. Actors

| Id  | Actor                                      | Capability assumed                                                                                                       |
| --- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| AC1 | Unauthenticated internet                   | Any request, any rate, rotating addresses, no account.                                                                   |
| AC2 | Hostile valid user                         | A real account and token. Can register keys, send signed batches, read own data, open issues and PRs on public surfaces. |
| AC3 | Compromised installation                   | A valid user, valid key in SecretStorage, genuine-looking events with lies. Signing proves the key, not the truth.       |
| AC4 | Compromised provider, plugin or dependency | Controls a model reply, a tool or MCP output, or a package the intake or healer imports.                                 |
| AC5 | Insider                                    | An operator or developer with legitimate access to the store, config or repositories.                                    |
| AC6 | Compromised healer worker                  | Code execution inside one job sandbox, with that job's scoped tokens only.                                               |

| Boundary     | Crosses                         | Trust change                                                                                                                   |
| ------------ | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| TB1 to TB2   | extension to nginx              | Client is hostile. Opt-in, locally redacted, signed. Nothing it says is trusted.                                               |
| TB2 to TB3   | nginx to agent-service          | nginx is the only ingress and sets X-Real-IP [V infra/nginx/locations.conf lines 22 and 29]. The service re-checks everything. |
| TB3 internal | handler to queue to store       | A request handler only validates, stores and enqueues. It never starts a model, shell, git job or deploy.                      |
| TB3 to TB4   | store to healer                 | Pull, never push. Read-only credential. Sanitized records only. Raw payload never leaves TB3.                                  |
| TB4 internal | scheduler to worker to reviewer | Each job in a disposable sandbox. Policy and credentials outside the workspace.                                                |
| TB4 to TB5   | healer to GitHub                | Only through the broker. Branch `wolverine/*`, draft PR, allowlisted repositories.                                             |
| TB5 to TB6   | merged code to release          | Only the release controller can authorise publication. The healer holds no such credential.                                    |
| TB6 to TB1   | release to users                | A published version reaches every user. Irreversible for installed copies.                                                     |

### 9.5 Prompt injection and the healer's inputs (L)

All of L01 to L12 share one design answer: report text is evidence of a symptom, never an instruction. It reaches a model
only inside the untrusted fence, after hidden content is stripped and flagged; the healer's goal comes from a fixed

## 10. Residual risk, stated plainly

- A valid installation can lie within its budget. Signing proves a key, not honesty. The design makes lies harmless (no
  write from one uncorroborated source) and bounded (budgets), not impossible.
- Redaction is pattern and allowlist based. A new secret shape can get through until it is added. Quarantine and the
  retention purge limit the damage.
- The intake shares a process and a host with agent-service, which holds the encryption key and can dispatch device
  commands [V ADR-143]. The import boundary test lowers the risk, it does not remove it (A14).
- A Redis outage stops telemetry on purpose (fail closed). The interactive path does not depend on it.
- The Marketplace cannot recall an installed extension. Rollback means shipping a fixed version.
- The healer's models can be misled in their analysis. The design only guarantees they cannot act without the broker and
  the policy.
- No claim is made that the sandbox cannot be escaped. Contract tests prove the stated boundaries only.

## 12. Where the plan and the code disagree

See ADR-229, section "Conflicts found while reading the code". The short list: the extension is a user session, not a
device token (A03); the agent-service limiter and counters fail open and its signature helpers are symmetric (A06, F15);
agent-service has no config table for kill switches (K01); the `/api/v1/agent` location has no rate zone (F01).
