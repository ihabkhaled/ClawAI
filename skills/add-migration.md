# Skill: Add a Migration

Migrations are generated by Prisma inside the owning service. They must be additive and reversible; destructive changes need a staged plan (add → backfill → cut over → drop later). The dev-container entrypoint runs `prisma migrate deploy` on boot.

## When to use

- Any `schema.prisma` change (new model, column, index, relation, enum value).
- A data backfill that must ship alongside a schema change.

## When NOT to use

- No schema change is involved → no migration.
- The change touches another service's database — it doesn't; each service migrates its own DB.

## Read first

- [`./resolve-task-context.md`](./resolve-task-context.md).
- [`../rules/05-infra-rules.md`](../rules/05-infra-rules.md), [`../rules/02-backend-rules.md`](../rules/02-backend-rules.md).
- Existing files under `apps/claw-<service>-service/prisma/migrations/` for the naming pattern.

## Repository discovery steps

1. Read `prisma/schema.prisma` and the latest migration to understand current state.
2. Check for existing `seed*.ts` scripts that may need new default rows.
3. Determine additive vs destructive; if a column must eventually be dropped, plan the dual-write/backfill window.

## Tests-first plan

- Repository spec exercising the new columns.
- Seed idempotency: running the seed twice does not duplicate rows.

## Implementation steps

1. Edit `schema.prisma` (see [`./add-prisma-model.md`](./add-prisma-model.md)); keep new columns nullable or defaulted for reversibility.
2. Run `npx prisma migrate dev --name <descriptive-name>` inside the service dir; review the generated SQL.
3. For data changes, write an additive backfill (new nullable column → populate → later make required in a follow-up migration). Never drop-and-recreate populated columns in one step.
4. Update `seed*.ts` if new default data (catalog entries, default policies, admin rows) is needed; keep it idempotent (upsert).
5. Confirm the entrypoint runs `prisma migrate deploy` so the migration applies on container start; rebuild the container (Prisma changes require a rebuild).

## Security considerations

- Never store secrets in seed data in plaintext; encrypted fields stay encrypted.
- Additive/reversible migrations avoid data loss (reversibility mindset).
- Do not add cross-service foreign keys — data ownership is per service.

## Failure modes

- Destructive migration with no backfill → data loss on deploy.
- Non-idempotent seed → duplicate rows on re-run.
- Forgetting the container rebuild → the new migration never applies in Docker.

## Validation commands

```bash
cd apps/claw-<service>-service && npx prisma migrate dev --name <name> && npm run typecheck && npm run lint && npm test && npm run build
```

Then rebuild: `./scripts/claw.sh service:rebuild claw-<service>-service` and verify the migration applied in logs.

## Documentation updates

- Update `docs/06-data/database-reference.md` with the new columns/models and any seed defaults.

## Definition of done

- Additive, reviewed migration; idempotent seed; tests green; container rebuilt with the migration applied; docs updated.
